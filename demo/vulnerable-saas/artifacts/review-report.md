# Code Review Report — vulnerable-saas

> Generated by `review` plugin (multi-agent code review with confidence filtering)

## CRITICAL (90–100)

### [100] Hardcoded Supabase service-role key in source code
**File:** `lib/supabase.ts:6,11`

The `supabaseServiceKey` is hardcoded as a string literal and the `supabaseAdmin` client using it is exported from this module. The service-role key bypasses all Row Level Security policies in Supabase. Anyone who can read the source (e.g., via a leaked bundle, public repo, or compromised CI) gets unrestricted database access.

Fix: move both keys to `process.env.NEXT_PUBLIC_SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, and never export `supabaseAdmin` from a shared module — instantiate it only inside server-side route handlers.

---

### [100] Service-role client used in every API route
**Files:** `app/api/notes/route.ts:2`, `app/api/users/route.ts:2`, `app/api/auth/reset/route.ts:11`

All three route files import and use `supabaseAdmin` (the service-role client). This means every query runs with superuser privileges, completely bypassing any RLS rules defined in Supabase.

Fix: use the per-request authenticated client (`createServerClient` from `@supabase/ssr`) that forwards the user's JWT, and rely on RLS for authorization.

---

### [100] IDOR — unauthenticated access to any user's notes
**File:** `app/api/notes/route.ts:6–19`

`GET /api/notes?user_id=xxx` accepts an arbitrary `user_id` with no session check. Any anonymous caller can enumerate all users' notes by cycling through UUIDs.

Fix: extract the authenticated user's ID from the session token server-side; ignore the `user_id` query param entirely.

---

### [100] Unauthenticated note deletion (broken access control)
**File:** `app/api/notes/route.ts:46–59`

`DELETE /api/notes?id=xxx` deletes any note by primary key with no ownership check and no authentication requirement.

Fix: require a valid session; verify the note's `user_id` matches the session user before deleting.

---

### [100] Mass assignment — caller can elevate their own role to admin
**File:** `app/api/users/route.ts:27–44`

`PATCH /api/users?id=xxx` passes `body` (the raw parsed request body) directly to `.update(body)`. A caller can send `{ "role": "admin", "is_admin": true }` and it will be written to the `profiles` table. No ownership check either.

Fix: maintain an explicit allowlist of mutable fields and verify `userId` matches the session.

---

### [100] Stored XSS via unsanitized HTML rendering
**File:** `components/NotesList.tsx:23–25,33`

Note content retrieved from the database is rendered directly as HTML without any sanitization. Combined with the unauthenticated POST endpoint, this is a trivially exploitable stored XSS.

Fix: sanitize with `DOMPurify.sanitize(html)` before rendering, or use plain text.

---

### [100] Unauthenticated note creation with no input validation or size limit
**File:** `app/api/notes/route.ts:23–42`

`POST /api/notes` accepts arbitrary JSON and writes it to the database with no authentication, no field-length validation, and no payload size cap.

Fix: require an authenticated session; validate and cap `title` and `content` lengths.

---

### [100] Wildcard CORS on all API routes
**File:** `next.config.js:8–13`

`Access-Control-Allow-Origin: *` combined with all methods and all headers allowed. Any origin can make arbitrary cross-origin requests.

Fix: restrict to the app's own domain.

---

### [98] Auth token stored in a non-httpOnly, non-secure, non-sameSite cookie
**File:** `app/api/auth/route.ts:29–34`

The Supabase JWT access token is stored in a cookie without `httpOnly: true`, `secure: true`, or `sameSite: 'lax'`. The token is readable by JavaScript (XSS token theft), sent over plain HTTP (network sniffing), and attached to cross-site requests (CSRF). 30-day `maxAge` means a stolen token stays valid for a month.

Fix: `{ httpOnly: true, secure: true, sameSite: 'lax', maxAge: 60 * 60 * 8 }`.

---

### [97] User enumeration via distinct auth error messages
**Files:** `app/api/auth/route.ts:16–25`, `app/api/auth/reset/route.ts:16–21`

Login returns 404 "User not found" vs 401 "Invalid password"; password reset returns 404 "No account with this email". Attackers can build a valid email list.

Fix: return a single uniform response regardless of whether the user exists.

---

### [96] Import statement after code in `reset/route.ts`
**File:** `app/api/auth/reset/route.ts:35`

`import` appears at the bottom of the file. Non-standard, will cause ESLint `import/first` errors.

Fix: move all imports to the top.

---

### [95] No rate limiting on password reset endpoint
**File:** `app/api/auth/reset/route.ts:6`

No rate limiting, no CAPTCHA, no cooldown. Email bombing vector.

Fix: implement per-IP and per-email rate limiting.

---

### [94] Internal Supabase error details leaked to client
**File:** `app/api/users/route.ts:16–19`

`error.details` and `error.hint` are Supabase/PostgreSQL internal fields containing schema structure.

Fix: log server-side; return only a generic error to the client.

## IMPORTANT (80–89)

### [88] Query parameter not URL-encoded
**File:** `components/UserSearch.tsx:10`

User-controlled `query` is interpolated without `encodeURIComponent()`.

Fix: use `encodeURIComponent(query)`.

---

### [87] Full user objects including email and role exposed in search
**File:** `app/api/users/route.ts:22`, `components/UserSearch.tsx:27–29`

Any unauthenticated caller can enumerate all users' email addresses and roles.

Fix: return only `{ id, display_name, avatar_url }`.

---

### [85] No session management — hardcoded user ID
**File:** `app/page.tsx:6`

`const currentUserId = "user-123"` — no functional session detection.

Fix: read the authenticated user's ID from the server-verified session.

---

### [84] `any[]` typed state — type safety absent
**Files:** `components/NotesList.tsx:6`, `components/UserSearch.tsx:7`

`useState<any[]>([])` suppresses all TypeScript safety guarantees.

Fix: define proper interfaces for API response shapes.

---

### [82] Empty search returns all users
**File:** `app/api/users/route.ts:7`

Omitting `search` dumps the full user list.

Fix: require minimum 2 characters, or return 400 if missing.

## Summary

**13 Critical + 5 Important** findings spanning OWASP Top 10.

### Most demo-friendly attack chain:
1. POST an XSS payload via `/api/notes` (no auth required)
2. Any user who views the notes list executes the payload
3. The payload reads `document.cookie` (no `httpOnly`) and exfiltrates the JWT
4. The JWT is used to PATCH the victim's profile to `role: "admin"` (mass assignment, no ownership check)

**Complete account takeover in 4 unauthenticated HTTP requests.**
